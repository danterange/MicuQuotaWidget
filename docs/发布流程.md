# 发布流程

## 版本规则

版本由根目录 `Directory.Build.props` 统一维护。`scripts/Invoke-Delivery.ps1 -Release` 自动递增 patch version，并同步：

- `Directory.Build.props`
- `README.md` 的版本标记
- `CHANGELOG.md`
- `docs/releases/vX.Y.Z.md`

## 本地到 GitHub 的顺序

1. 质量门禁和代码审查全部通过。
2. 脚本精确暂存本次任务文件并创建本地 commit。
3. 验证 `origin`、分支和待推送范围后执行普通 `git push`，禁止 force push。
4. 推送 tag 后由 `.github/workflows/release.yml` 在干净的 Windows runner 使用 `dotnet publish` 生成 `win-x64` ZIP 和 `SHA256SUMS.txt`。
5. GitHub Actions 使用 `gh release create` 创建非草稿 GitHub Release，附件包括 ZIP 与哈希文件。
6. 本地脚本等待对应 commit 的 Actions 成功，随后下载附件并复核 SHA-256。

发布工作流将第三方 Action 固定到不可变 commit SHA，检出阶段不持久化凭据；仅 `gh release create` 读取 GitHub Actions 提供的短期 token。tag 通过环境变量传入并按 `vMAJOR.MINOR.PATCH` 校验，不插入 PowerShell 源码。除 build 与 test 外，工作流还运行 `scripts/Test-Ui.ps1`，以渲染并验证主小组件和设置窗口截图。发布预检中，目标 tag 尚不存在 Release（包括空 Release 列表）是正常情况；Release 列表查询或其他 GitHub CLI 查询失败必须停止发布。预检还须核对精确暂存路径，扫描高风险秘密与本机路径，并拒绝含个人 Git Author/Committer 元数据的历史。

自动创建的公开 commit 和注释 tag 固定使用项目通用 noreply Git 身份，不继承本机全局 Git 用户配置。若已推送历史意外包含私人信息或非批准身份，必须停止发版；对刚创建且无人依赖的仓库，应在明确授权后删除并以干净的匿名历史重新创建，不能通过新增提交掩盖问题。

没有配置远端或 GitHub CLI 认证时，脚本必须安全停止并说明缺失项；不得猜测仓库地址、创建远端、泄露 Token 或伪称已经发布。
